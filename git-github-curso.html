Módulo 01 Fácil

Fundamentos de Git

Empieza por entender qué es Git, cómo se diferencia de otros sistemas de control de versiones y cuáles son los comandos del día a día.

¿Qué es Git?

Git es un sistema de control de versiones distribuido. Esto significa que cada desarrollador tiene una copia completa del historial del proyecto en su máquina, no solo un snapshot del estado actual. Esto permite trabajar offline, crear ramas locales sin afectar al equipo y tener redundancia natural.

Distribuido vs centralizado: En sistemas centralizados (como SVN), existe un único servidor con el historial. En Git, cada clon es un repositorio completo.

Inicializar un repositorio

Para convertir un directorio cualquiera en un repositorio Git:

git init

Este comando crea una carpeta oculta .git con toda la estructura interna del repositorio (objetos, refs, configuración).

Configuración inicial

Antes de hacer tu primer commit, configura tu identidad globalmente:

git config --global user.name "Tu Nombre"
git config --global user.email "tu@email.com"

Los estados de un archivo

En Git, un archivo puede estar en uno de estos estados:

EstadoDescripción
untrackedGit no lo conoce aún
unmodifiedSin cambios respecto al último commit
modifiedModificado pero no preparado
stagedPreparado para el próximo commit
?
En el quiz: "Pushed" no es un estado interno de Git. Subir al remoto no cambia el estado del archivo, solo sincroniza el historial.

El ciclo básico

El flujo de trabajo más común consiste en cuatro pasos:

git status                    # qué cambió
git add archivo.py            # preparar para commit
git commit -m "feat: ..."     # confirmar
git log                       # revisar historial

Variantes útiles de git add:

  • git add . — agrega todos los cambios del directorio actual
  • git add --all — agrega todos los cambios del repo (incluye eliminaciones)
  • git add -u — solo archivos ya rastreados
  • git add -p — interactivo, agrega cambios por trozos (hunks)

Ver diferencias

git diff              # working tree vs staging
git diff --staged     # staging vs último commit
git diff HEAD         # working tree vs último commit

Ignorar archivos: .gitignore

Crea un archivo .gitignore en la raíz del repositorio con los patrones que Git debe omitir:

node_modules/
.env
*.log
__pycache__/
.DS_Store
Tip: Si un archivo ya estaba rastreado antes de añadirlo a .gitignore, debes eliminarlo del índice con git rm --cached archivo.
Módulo 02 Fácil

Ramas (Branches)

Las ramas son lo que hace a Git tan poderoso. Aprende qué son realmente y cómo trabajar con ellas eficientemente.

¿Qué es una rama?

Una rama en Git es simplemente un puntero móvil que apunta a un commit. No es una copia del código, no es un directorio: es un archivo de 41 bytes que contiene el hash SHA-1 del último commit de esa línea de desarrollo.

Esto explica por qué crear y cambiar ramas en Git es prácticamente instantáneo, incluso en repositorios gigantes.

Listar ramas

git branch          # ramas locales
git branch -a       # locales + remotas
git branch -r       # solo remotas
git branch -v       # con el último commit de cada una

Crear y cambiar de rama

Hay dos formas equivalentes:

# Forma clásica (cualquier versión de Git)
git checkout -b feature-login

# Forma moderna (Git 2.23+)
git switch -c feature-login
checkout vs switch: Desde Git 2.23 se introdujo git switch (solo para ramas) y git restore (solo para archivos), separando las dos responsabilidades de checkout.

Cambiar de rama existente

git switch main
git checkout main         # equivalente

Eliminar ramas

git branch -d feature-login   # solo si está fusionada
git branch -D feature-login   # forzar eliminación
Cuidado: -D elimina la rama incluso si tiene commits que no están en otra parte. Si no estaban en remoto, esos commits se pierden (aunque git reflog puede ayudar a recuperarlos).

Renombrar la rama actual

git branch -m nuevo-nombre
?
En el quiz: Una rama es un puntero móvil — Verdadero. Es uno de los conceptos fundamentales que diferencia a Git de otros VCS.
Módulo 03 Fácil

Trabajo con Remotos

Los repositorios remotos son la base del trabajo colaborativo. Aprende a sincronizarte con ellos sin perder cambios en el camino.

Clonar un repositorio

git clone https://github.com/usuario/repo.git

Esto descarga el repositorio completo, incluyendo todo el historial de commits, todas las ramas remotas y la configuración de origen.

Ver y gestionar remotos

git remote -v                              # listar remotos con URLs
git remote add origin URL                  # añadir remoto
git remote remove origin                   # quitar remoto
git remote set-url origin nueva-url        # cambiar URL

Sincronizar: fetch vs pull

ComandoQué hace
git fetchDescarga referencias remotas SIN modificar el working tree
git pullfetch + merge automático
git pull --rebasefetch + rebase (historial lineal)
Tip profesional: Usar git fetch antes de cualquier operación importante te permite ver qué cambió en el remoto sin sorpresas. Es la operación más segura para sincronizar.

Empujar cambios

git push                          # push a la rama tracked
git push origin feature-login     # especificar remoto y rama
git push -u origin feature-login  # primera vez, establece tracking

main vs master

En octubre de 2020, GitHub cambió el nombre por defecto de la rama principal de master a main en todos los repositorios nuevos. Es una buena práctica adoptar este cambio en proyectos nuevos.

?
En el quiz: La diferencia clave entre fetch y pull: fetch solo descarga, no modifica nada de tu trabajo actual. pull descarga y fusiona automáticamente.
Módulo 04 Medio

Merging & Rebasing

Integrar trabajo de varias ramas es donde Git muestra su verdadero poder. Aprende cuándo usar merge, cuándo rebase y cómo resolver conflictos sin pánico.

git merge

Combina los cambios de una rama en otra. Hay dos escenarios principales:

Fast-forward

Si la rama destino no tiene commits nuevos desde que se creó la rama feature, Git simplemente mueve el puntero hacia adelante. No crea un commit de merge.

git switch main
git merge feature-login   # fast-forward si es posible

Merge commit

Si ambas ramas tienen commits nuevos, Git crea un commit especial con dos padres que registra la fusión.

git merge --no-ff feature-login   # forzar merge commit aunque sea ff
Estrategias de merge en Git: recursive (default), ours, theirs, octopus (para fusionar más de 2 ramas), resolve, subtree. cherry-pick NO es una estrategia de merge — es un comando aparte.

git rebase

Rebase "reescribe" la historia de tu rama colocando tus commits sobre la punta de otra rama, generando nuevos SHA-1 para cada commit movido.

git switch feature-login
git rebase main

El resultado es un historial lineal, sin merge commits, como si hubieras desarrollado feature-login partiendo de la última versión de main.

Regla de oro del rebase: nunca hagas rebase de commits que ya hayan sido empujados a una rama compartida. Reescribir historial público causa caos en el equipo.

pull --rebase

Una mejor alternativa a git pull en muchos casos:

git pull --rebase   # fetch + rebase, historial lineal

Tus commits locales se aplican encima de los nuevos del remoto, evitando merge commits innecesarios cuando solo querías sincronizar.

Resolución de conflictos

Cuando Git no puede fusionar automáticamente, marca el conflicto en el archivo:

<<<<<<< HEAD
versión actual de tu rama
=======
versión que viene de la otra rama
>>>>>>> feature-login

Pasos para resolver:

  1. Editar el archivo: dejar la versión correcta (puede ser una mezcla de ambas)
  2. Eliminar los marcadores <<<, ===, >>>
  3. git add archivo para marcar como resuelto
  4. git commit (en merge) o git rebase --continue (en rebase)

Si te arrepientes a mitad de una operación:

git merge --abort
git rebase --abort

Three-way merge: cómo funciona internamente

Cuando dos ramas divergieron, Git encuentra el LCA (Lowest Common Ancestor) — el commit más reciente que ambas comparten. Compara cada rama con ese ancestro y combina automáticamente los cambios que no se solapen.

Solo aparece un conflicto cuando ambas ramas modificaron la misma línea del mismo archivo de forma diferente respecto al ancestro común.

Estrategia "ort": Desde Git 2.33 la estrategia por defecto es ort (Ostensibly Recursive's Twin), que reemplazó a recursive. Es más rápida y maneja mejor renames y casos borde.

Rebase interactivo (git rebase -i)

Permite reescribir el historial commit por commit. Al ejecutarlo, Git abre un editor con la lista de commits y un comando para cada uno:

git rebase -i HEAD~4
ComandoAcción
pickMantiene el commit tal cual
rewordMantiene los cambios pero edita el mensaje
editPausa para modificar el commit
squashCombina con el anterior, fusiona mensajes
fixupComo squash pero descarta el mensaje
dropElimina el commit completo

Push forzado seguro: --force-with-lease

Si reescribes commits ya empujados (con rebase o amend), necesitas forzar el push. Pero --force puede sobrescribir trabajo ajeno sin avisar. La alternativa segura:

git push --force-with-lease

Solo fuerza el push si nadie más ha empujado a esa rama desde tu último fetch. Si alguien lo hizo, falla y te protege.

Regla: usa --force-with-lease en lugar de --force siempre que puedas. Solo recurre a --force cuando sepas exactamente lo que hace el comando.
?
En el quiz: Recuerda que git merge NO siempre crea un merge commit — si es fast-forward, solo mueve el puntero. Para forzar el commit usa --no-ff.
Módulo 05 Medio

GitHub Workflow

GitHub añade una capa de colaboración sobre Git. Conoce los conceptos esenciales para trabajar profesionalmente en equipo.

Forks

Un fork es una copia personal de un repositorio ajeno en tu cuenta de GitHub. Te permite experimentar libremente sin afectar el original. El flujo típico:

  1. Hacer fork del repo en GitHub
  2. Clonar tu fork localmente
  3. Crear una rama, hacer cambios, push a tu fork
  4. Abrir un Pull Request al repo original

Pull Requests

Un Pull Request (PR) es la solicitud formal para integrar cambios de una rama a otra (o de un fork al repo original). En GitLab se llama Merge Request (MR), pero el concepto es idéntico.

Un buen PR incluye:

  • Título descriptivo y conciso
  • Descripción del problema y la solución
  • Capturas o ejemplos cuando aplique
  • Checklist de testing
  • Referencias a issues relacionados

Code Review

GitHub permite comentar línea por línea, sugerir cambios directamente con suggested changes y aprobar o solicitar cambios formalmente. Es la herramienta principal para garantizar calidad en equipo.

README.md

GitHub renderiza automáticamente el archivo README.md de la raíz como página de presentación del repositorio. Un buen README incluye:

  • Descripción del proyecto
  • Instalación y dependencias
  • Ejemplos de uso
  • Cómo contribuir
  • Licencia

Issues, Labels y Milestones

GitHub ofrece un sistema integrado de tracking:

  • Issues: bugs, features y discusiones
  • Labels: categorización (bug, enhancement, good-first-issue)
  • Milestones: agrupar issues hacia un objetivo concreto
  • Projects: tableros tipo Kanban
Tip: Vincula commits con issues escribiendo Closes #42 en el mensaje del commit. Cuando el PR se fusione, GitHub cerrará automáticamente el issue #42.

Estrategias de merge en Pull Requests

GitHub ofrece tres formas de integrar un PR:

EstrategiaResultado en main
Create a merge commitConserva todos los commits + un merge commit
Squash and mergeCombina todos los commits del PR en uno solo
Rebase and mergeAplica los commits en main sin merge commit (lineal)

Squash and merge es la opción más popular en equipos modernos: produce un historial limpio en main donde cada commit corresponde a una feature.

Plantillas de Pull Request e Issues

Para que cada PR tenga estructura consistente, crea .github/PULL_REQUEST_TEMPLATE.md:

## Descripción
<!-- ¿Qué hace este PR? -->

## Tipo de cambio
- [ ] Bug fix
- [ ] Feature
- [ ] Refactor

## Checklist
- [ ] Tests añadidos
- [ ] Docs actualizadas

Equivalente para issues: .github/ISSUE_TEMPLATE/bug.md y feature.md.

CODEOWNERS — revisores automáticos

El archivo .github/CODEOWNERS asigna propietarios por path. GitHub los añade como reviewers automáticos en cada PR que toque sus archivos:

# Propietarios globales
*           @equipo-arquitectura

# Frontend
/src/web/   @ana @luis

# Backend
/api/       @backend-team

# Docs
*.md        @docs-team

Permisos de colaborador

GitHub define 5 niveles de permisos para repositorios:

PermisoCapacidades
ReadSolo lectura, clonar, abrir issues
TriageRead + gestionar issues y PRs (sin commit)
WriteTriage + push a ramas, gestionar releases
MaintainWrite + gestionar configuración del repo (sin acciones destructivas)
AdminControl total: settings, eliminar repo, gestionar accesos

GitHub Environments

Los Environments son entornos lógicos de despliegue (production, staging, dev) con sus propias reglas:

  • Required reviewers: aprobación manual antes del deploy
  • Wait timer: retraso configurable
  • Branch restrictions: solo ciertas ramas pueden desplegar
  • Secrets propios: credenciales aisladas por entorno

GitHub Packages

Registro de paquetes integrado en GitHub. Soporta múltiples ecosistemas: npm, Maven, RubyGems, Docker, NuGet. La autenticación usa el mismo token de GitHub.

npm publish --registry https://npm.pkg.github.com

GitHub Codespaces

Entornos de desarrollo en la nube basados en VS Code. La configuración vive en .devcontainer/devcontainer.json:

{
  "name": "Mi proyecto",
  "image": "mcr.microsoft.com/devcontainers/python:3.12",
  "features": { "ghcr.io/devcontainers/features/node:1": {} },
  "extensions": ["ms-python.python", "ms-toolsai.jupyter"],
  "postCreateCommand": "pip install -r requirements.txt"
}

Cualquier colaborador puede abrir el repo en un Codespace y tener exactamente el mismo entorno preconfigurado, sin instalar nada localmente.

Módulo 06 Difícil

Comandos Avanzados

Los comandos que diferencian a un usuario casual de uno profesional. Aprende a recuperar trabajo perdido, mover commits con precisión y manipular la historia.

git stash — guardar trabajo en progreso

Cuando necesitas cambiar de rama pero tienes cambios sin commitear:

git stash                          # guarda y limpia el working tree
git stash push -m "wip: feature"   # con mensaje
git stash list                     # ver stashes guardados
git stash pop                      # aplica y elimina el último
git stash apply stash@{2}          # aplica uno específico
git stash drop stash@{0}           # elimina uno específico

git cherry-pick — copiar commits específicos

Aplica un commit existente sobre la rama actual:

git cherry-pick abc1234            # un commit
git cherry-pick abc1234..def5678   # un rango

Útil cuando necesitas un fix específico de otra rama sin fusionarla completa.

git reset — mover el puntero

Cambia a qué commit apunta la rama actual. Tiene tres modos:

ModoWorking treeStagingHEAD
--softSin cambiosSin cambiosMovido
--mixed (default)Sin cambiosResetMovido
--hardResetResetMovido
 
git reset --soft HEAD~1    # deshace el último commit, mantiene cambios staged
git reset HEAD~1            # deshace y unstaged
git reset --hard HEAD~1     # destruye el último commit completo
Peligro: --hard es destructivo. Si los commits no están en remoto y no hay reflog reciente, los pierdes.

git revert — deshacer sin reescribir

Crea un nuevo commit que revierte los cambios de un commit anterior. Es la forma segura de "deshacer" en una rama compartida porque no reescribe el historial.

git revert abc1234

git reflog — el seguro de Git

Git mantiene un log de cada cambio de HEAD durante 90 días por defecto. Si "perdiste" commits con un reset --hard o branch -D:

git reflog
# 1a2b3c4 HEAD@{2}: commit: feature en progreso
# 9z8y7x6 HEAD@{3}: reset: moving to HEAD~1

git reset --hard HEAD@{2}    # recuperar

Repositorio bare

Un repo bare no tiene working directory — solo los datos de Git. Se usa típicamente como repositorio central en servidores. Las URLs que terminan en .git suelen ser bare.

git init --bare proyecto.git
git clone --bare repo proyecto.git

Detached HEAD

Cuando haces git checkout <hash> en lugar de a una rama, HEAD apunta directamente a un commit. Es el estado "detached HEAD". Cualquier commit nuevo no pertenecerá a ninguna rama y se puede perder.

git checkout abc1234         # detached HEAD
git switch -c nueva-rama     # rescatar creando rama desde aquí

Tags: marcar versiones

Hay dos tipos:

  • Lightweight: solo un puntero a un commit
  • Annotated: objeto Git completo con autor, fecha, mensaje y firma opcional
git tag v1.0                              # lightweight
git tag -a v1.0 -m "Release 1.0"          # annotated (recomendado)
git push origin v1.0                       # subir el tag
git push origin --tags                     # subir todos los tags

Firmar commits con GPG

Para producir commits criptográficamente verificables (GitHub muestra badge "Verified"):

git commit -S -m "feat: ..."   # firma con clave GPG configurada
git config commit.gpgsign true # firmar siempre por defecto

Inspeccionar el log con flags útiles

git log --oneline                          # una línea por commit
git log --oneline --graph --all            # árbol visual de todas las ramas
git log --author="Ana"                     # filtrar por autor
git log --since="2 weeks ago"              # últimas 2 semanas
git log --grep="bug"                       # buscar en mensajes
git log -p archivo.py                      # mostrar diffs de un archivo

Comparar ramas y archivos

git diff main..feature          # cambios en feature que no están en main
git diff main...feature         # cambios desde el ancestro común
git diff HEAD~3 HEAD            # comparar dos commits cualesquiera
git diff --stat                 # resumen estadístico

Descartar cambios locales

git checkout -- archivo.txt    # descartar cambios (Git < 2.23)
git restore archivo.txt        # alternativa moderna (Git 2.23+)
git restore --staged archivo   # quitar del staging area

Limpiar referencias remotas obsoletas

git fetch --prune              # elimina refs remotas que ya no existen
git remote prune origin        # equivalente

Eliminar ramas remotas

git push origin --delete feature   # forma moderna (recomendada)
git push origin :feature           # sintaxis clásica equivalente

git bisect — encontrar el commit que rompió algo

Búsqueda binaria automatizada para localizar la regresión:

git bisect start
git bisect bad                  # el commit actual está roto
git bisect good v1.0            # esta versión funcionaba
# Git hace checkout al punto medio. Pruebas y marcas:
git bisect good                 # o git bisect bad
# ...repetir hasta que Git encuentre el commit culpable
git bisect reset                # finalizar

Tracking de ramas remotas

git branch -vv                  # muestra qué rama remota trackea cada local
git branch --set-upstream-to=origin/main main

Shallow clone — historial mínimo

Para CI/CD donde el historial completo no importa:

git clone --depth=1 URL         # solo el último commit
git fetch --unshallow           # convertir a clone completo si lo necesitas

Inspeccionar objetos Git

git cat-file -t <hash>          # tipo del objeto (blob/tree/commit/tag)
git cat-file -p <hash>          # contenido del objeto
git ls-tree HEAD                # listar contenido del tree del último commit

Mantenimiento del repositorio

git gc                          # garbage collection: compacta objetos
git gc --aggressive             # más lento, pero comprime mejor
git fsck                        # verifica integridad de objetos
.git/packed-refs: Cuando un repo tiene muchas ramas/tags, Git agrupa esas referencias en un único archivo packed-refs para mejor rendimiento, en lugar de tener miles de archivos pequeños en .git/refs/.
Módulo 07 Experto

Nivel Experto

Los temas que aparecen en entrevistas senior y en arquitecturas de equipos grandes. No necesitas dominarlos para usar Git, pero sí para destacar.

Git object model: el modelo de objetos

El Git object model es la base de todo el sistema. Git almacena cuatro tipos de objetos, todos inmutables y identificados por su hash SHA-1:

  • blob: contenido de un archivo
  • tree: directorio (lista de blobs y otros trees)
  • commit: snapshot que apunta a un tree + metadatos + padres
  • tag: referencia anotada a un commit (annotated tag)

Las ramas no son objetos — son simplemente referencias (refs) que apuntan a un commit.

Todo el repositorio forma un DAG (Directed Acyclic Graph): los commits apuntan a trees y a sus padres, los trees apuntan a blobs y otros trees. Cada objeto vive en .git/objects/.

Refs especiales: ORIG_HEAD, MERGE_HEAD, CHERRY_PICK_HEAD

Git mantiene refs temporales durante operaciones complejas:

  • ORIG_HEAD — guarda HEAD antes de operaciones potencialmente peligrosas (reset, merge). Para deshacer: git reset ORIG_HEAD
  • MERGE_HEAD — apunta al commit de la rama que se está fusionando (mientras hay un merge en curso)
  • CHERRY_PICK_HEAD — apunta al commit que se está cherry-pickeando

Comandos que reescriben historial

Los siguientes comandos modifican o eliminan commits existentes:

  • git rebase — mueve commits, generando nuevos SHAs
  • git commit --amend — modifica el último commit
  • git reset --hard — elimina commits del historial
  • git filter-branch / git-filter-repo — reescribe completamente

git revert NO reescribe historial: crea un nuevo commit que invierte los cambios.

Regla de oro: nunca reescribas historial que ya fue empujado a una rama compartida. Las nuevas refs no coincidirán con las que tienen los demás.

git fsck — verificar integridad

git fsck                    # verifica todos los objetos
git fsck --lost-found       # encuentra objetos huérfanos recuperables

git rerere — REuse REcorded REsolution

Si activas rerere, Git memoriza cómo resolviste cada conflicto y aplica la misma resolución automáticamente la próxima vez que aparezca:

git config --global rerere.enabled true

Especialmente útil en ramas de larga vida o rebases frecuentes que generan los mismos conflictos repetidamente.

git notes — metadatos sin alterar commits

Permite añadir notas a commits sin cambiar su SHA. Útil para CI: pegar resultados de tests, coverage o reviews sin reescribir historial:

git notes add -m "Coverage: 87%" abc1234
git log --show-notes

git replace — sustituir objetos

Crea referencias en refs/replace/ que mapean transparentemente un objeto a otro:

git replace abc1234 def5678            # sustituye objeto
git replace --graft commit padre1 padre2   # cambia padres sin reescribir

Útil para conectar historiales de repositorios separados o corregir metadata sin alterar SHAs.

commit-graph — acelerador de historial

Archivo binario en .git/objects/info/commit-graph que pre-calcula metadata (generation numbers, tree hashes) para acelerar drásticamente operaciones como git log, merge-base y queries de reachability en repos grandes.

git commit-graph write --reachable

git maintenance — mantenimiento automático

Sistema de tareas programadas (Git 2.29+) que mantiene el rendimiento del repo:

git maintenance start    # registra cron/launchd task
# Tareas: gc parcial, prefetch, commit-graph, pack-refs, etc.

Partial clone

Reduce drásticamente el tamaño inicial de un clone descargando objetos bajo demanda:

git clone --filter=blob:none URL    # blobless: sin contenido de archivos
git clone --filter=tree:0 URL       # treeless: solo commits

Los blobs/trees se descargan automáticamente cuando los necesitas.

Sparse-checkout — solo paths que necesitas

Para monorepos donde solo trabajas con una parte del código:

git sparse-checkout init --cone
git sparse-checkout set apps/web packages/ui

El working tree solo materializa los directorios indicados, ahorrando espacio y acelerando operaciones.

Git LFS (Large File Storage)

Sin LFS, cada versión de un binario grande se duplica en el historial. Con LFS, el repo solo guarda punteros de texto; el contenido real vive en un servidor LFS y se descarga bajo demanda:

git lfs install
git lfs track "*.psd"
git lfs track "models/*.bin"
git add .gitattributes

Git Hooks (cliente y servidor)

Scripts que Git ejecuta automáticamente. Viven en .git/hooks/.

Hooks del lado del cliente:

  • pre-commit — antes de crear un commit (linting, tests)
  • commit-msg — validar formato del mensaje
  • pre-push — antes de subir al remoto
  • post-merge — después de fusionar (reinstalar deps, etc.)

Hooks del lado del servidor:

HookCuándo y para qué
pre-receiveUna sola vez por push, antes de aceptar nada. Puede rechazar todo.
updatePor cada ref individual. Puede rechazar ramas específicas.
post-receiveTras aceptar todo. Ideal para webhooks, CI, notificaciones.
post-updateSimilar a post-receive pero recibe solo los nombres de las refs.

Para hooks de cliente compartidos en equipo, usa Husky (JS) o pre-commit (Python).

git worktree — múltiples directorios de trabajo

Permite tener varios working directories del mismo repo, cada uno en una rama distinta. Sin clonar, sin stash:

git worktree add ../hotfix main         # nuevo working tree en ../hotfix
git worktree list                       # ver todos los worktrees
git worktree remove ../hotfix

GitHub Actions avanzado

Build matrix (paralelización)

jobs:
  test:
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [18, 20, 22]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: ${{ matrix.node }} }

Esto ejecuta 9 jobs en paralelo (3 SO × 3 versiones de Node).

Job dependencies con needs

jobs:
  build:  { runs-on: ubuntu-latest, steps: [...] }
  test:   { needs: build, runs-on: ubuntu-latest, steps: [...] }
  deploy: { needs: [build, test], runs-on: ubuntu-latest, steps: [...] }

GitHub Advanced Security (GHAS)

Suite de seguridad enterprise que incluye:

  • CodeQL: análisis estático (SAST) para encontrar vulnerabilidades en el código
  • Secret scanning + push protection: bloquea pushes con secretos detectados
  • Dependency review: alerta sobre dependencias vulnerables en PRs
  • Security overview: dashboard centralizado de seguridad

Supply chain security

Mecanismos clave para proteger la cadena de suministro:

  • Dependabot alerts: notifica vulnerabilidades en dependencias
  • Secret scanning: detecta credenciales filtradas
  • Code scanning con CodeQL: análisis estático automatizado
  • Signed commits: GPG o Sigstore/gitsign

Las branch protection rules son governance, no supply chain security.

Sigstore / gitsign — firma sin gestionar claves

Alternativa moderna a GPG: usa identidades OIDC (GitHub, Google) y certificados efímeros. Las firmas se publican en Rekor, un transparency log público:

brew install sigstore/tap/gitsign
gitsign verify HEAD

Pack protocol y Git protocol v2

El pack protocol negocia y transfiere packfiles (objetos comprimidos) entre cliente y servidor durante clone/fetch/push.

El protocolo Git v2 mejora el original con:

  • Capability advertisement simplificado
  • Reducción de overhead en repos con muchas refs
  • Soporte nativo de partial clone filters
  • object-info para consultar metadata sin descargar

Funciona sobre HTTP/1.1, SSH y sockets — no requiere HTTP/2.

Monorepos con Turborepo

Build system que serializa el grafo de tareas de un monorepo y cachea resultados. Solo re-ejecuta tareas cuando los inputs cambiaron:

turbo run build --filter=web

Puede usar el caché remoto de GitHub Actions como backend, evitando recompilaciones entre runs y entre desarrolladores.

GitOps con Argo CD / Flux

Paradigma donde el repositorio Git es la única fuente de verdad de la infraestructura:

  1. Un PR actualiza manifiestos YAML en el repo
  2. GitHub Actions valida y fusiona
  3. Argo CD / Flux detecta el cambio y sincroniza el clúster automáticamente

Importante: el CI nunca hace push directo al clúster. El clúster tira de Git, no recibe pushes externos.

git filter-branch / git-filter-repo

Para reescribir el historial completo (eliminar archivos sensibles que se commitearon, cambiar el email del autor, etc.):

# git-filter-repo es la alternativa moderna recomendada
git filter-repo --path archivo-secreto.txt --invert-paths

Modelos de branching

ModeloFilosofíaCuándo usarlo
Trunk-basedUna sola rama larga (main), feature branches cortas (< 1 día)Equipos con CI/CD maduro y deploy continuo
Git FlowRamas long-lived: develop, release, hotfix, featureReleases programados, software con versionado fuerte
GitHub Flowmain + feature branches con PRSaaS, deploy frecuente
Recomendación: En 2026, la mayoría de equipos web modernos usan GitHub Flow o Trunk-based. Git Flow está cayendo en desuso para SaaS pero sigue siendo válido para software con releases versionados.

uv · Python El gestor de paquetes moderno

uv es el gestor de paquetes y proyectos de Python que reemplaza a pip, pip-tools, pipx, poetry, pyenv y virtualenv — todo en un solo binario escrito en Rust, entre 10 y 100× más rápido. Este curso te lleva desde una analogía simple (construcción) hasta los workflows expertos en CI/CD.

Módulo 01 Fácil

¿Qué es uv y por qué existe?

Antes de tocar un comando, entiende el problema que resuelve. Vamos a explicarlo de dos formas: primero con una analogía sencilla para que cualquiera lo entienda, y luego con la versión técnica.

El problema en una frase

Los proyectos de Python necesitan paquetes externos (librerías como pandas, requests, numpy). Instalar esos paquetes, fijar sus versiones exactas, aislarlos por proyecto y mantener todo reproducible siempre fue lento, frágil y necesitaba combinar varias herramientas distintas.

uv hace todo eso, en un solo binario, increíblemente rápido.

Explicado con una analogía simple (para alguien que nunca tocó Python)

Imagina que diriges la construcción de varios edificios al mismo tiempo, cada uno para un cliente distinto. Cada obra tiene su propio diseño, requiere materiales específicos, debe construirse con sus equipos y bodegas aislados de las demás obras, y debe poder reproducirse al milímetro si años después el cliente pide una copia idéntica.

En esta operación:

  • Un material de construcción (concreto, acero estructural, vidrio templado) = un paquete de Python (ej: pandas, requests, numpy).
  • Una obra = un proyecto de Python (tu app, tu API, tu modelo de ML).
  • Las especificaciones técnicas del proyecto —planos y memoria descriptiva— = el archivo pyproject.toml. Describe qué necesitas en términos generales: "concreto resistencia 250 kg/cm²", "requests versión 2 o superior".
  • La orden de compra detallada con proveedor, número de lote y certificados de calidad = el archivo uv.lock. Versiones precisas de cada paquete y de los paquetes que ESOS paquetes requieren, para que la obra sea reproducible idéntica siempre.
  • La bodega de obra dedicada donde se almacenan SOLO los materiales de UN edificio, sin mezclar con los de otra obra = un entorno virtual (la carpeta .venv dentro del proyecto).
  • La maquinaria base sobre la que opera todo el equipo —grúas, andamios, sistema eléctrico de obra— = la versión de Python (3.11, 3.12, etc.). Cada obra puede requerir un equipamiento distinto.
  • uv = el contratista general que coordina todo: levanta órdenes a proveedores, recibe los materiales, los acomoda en la bodega correcta de cada obra, instala la maquinaria base y deja la cancha lista para que la cuadrilla construya. Y lo hace ~10–100× más rápido que el contratista anterior (pip).

Antes de uv tenías que coordinar varios proveedores especializados: uno para los materiales (pip), otro para asignar bodegas (virtualenv), otro para conseguir la maquinaria base correcta (pyenv), otro para registrar los lotes exactos (pip-tools) y otro para la herramienta de cuadrilla (pipx). uv hace todo eso solo, en un solo binario.

Versión técnica

uv es una herramienta de línea de comandos escrita en Rust, mantenida por Astral (los mismos creadores de ruff). Cubre tres responsabilidades:

  1. Resolver e instalar dependencias: reemplaza a pip y pip-tools.
  2. Gestionar entornos virtuales: reemplaza a virtualenv y venv.
  3. Gestionar versiones de Python: reemplaza a pyenv (descarga binarios oficiales precompilados).

Adicionalmente cubre la instalación de herramientas CLI (uv tool, en lugar de pipx) y la gestión completa de proyectos al estilo poetry (uv add, uv sync, uv lock).

¿Por qué es tan rápido?

  • Está escrito en Rust con paralelismo agresivo.
  • Usa un caché global con hardlinks/copy-on-write: si ya descargaste numpy 1.26 en otro proyecto, no lo descarga de nuevo, lo enlaza.
  • El resolutor de dependencias (PubGrub) detecta conflictos sin hacer descargas innecesarias.

Comparativa típica

Operaciónpipuv
Crear venv + instalar Django~6 s< 1 s
Resolver e instalar 100 paquetes30–60 s1–3 s
Cold install (sin caché) de un proyecto medio40–90 s3–8 s
Tip: los números dependen de tu máquina y red, pero el orden de magnitud (10–100×) se mantiene. La diferencia se siente sobre todo en CI/CD, donde cada segundo cuenta.
Qué deberías poder hacer ahora
  • Explicar con tus propias palabras (o con la analogía de la construcción) qué hace uv
  • Saber qué herramientas tradicionales reemplaza
  • Entender por qué es 10–100× más rápido que pip
Módulo 02 Fácil

Instalación y comandos diarios

De cero a un proyecto Python funcionando — y los comandos que vas a usar el 95% del tiempo después. Sin Python instalado previamente: uv mismo lo descarga.

Instalar uv

uv se distribuye como un binario único, sin dependencias. Elige según tu sistema:

macOS / Linux

curl -LsSf https://astral.sh/uv/install.sh | sh

Windows (PowerShell)

powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

Vía Homebrew (macOS)

brew install uv

Vía pipx (si ya tienes Python)

pipx install uv
Tip: el script oficial install.sh coloca uv en ~/.local/bin/ y no requiere sudo. Reinicia tu terminal o haz source ~/.bashrc después de instalar.

Verificar la instalación

uv --version
# uv 0.5.x

Crear tu primer proyecto

Un solo comando crea un proyecto completo, con su pyproject.toml, su .python-version y un README.md:

uv init mi-proyecto
cd mi-proyecto

Esto genera la siguiente estructura:

mi-proyecto/
├── .python-version       # versión de Python a usar (ej. 3.12)
├── pyproject.toml        # las "especificaciones": metadata + dependencias
├── README.md
├── main.py               # un script de ejemplo: print("Hello!")
└── .gitignore

El pyproject.toml que crea es mínimo y limpio:

[project]
name = "mi-proyecto"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.12"
dependencies = []

Añadir tu primera dependencia

Vamos a instalar requests (la librería para hacer HTTP en Python):

uv add requests

Esto, en un solo comando, hace cinco cosas:

  1. Crea automáticamente un entorno virtual .venv/ si no existe.
  2. Descarga la versión de Python correcta (si no la tienes).
  3. Resuelve requests y todas sus dependencias.
  4. Las instala en .venv/.
  5. Añade requests a pyproject.toml y bloquea las versiones exactas en uv.lock.

Ejecutar código con uv run

No necesitas activar el venv manualmente. uv run ejecuta cualquier comando dentro del entorno del proyecto:

uv run main.py
# Hello from mi-proyecto!

uv run python -c "import requests; print(requests.__version__)"
# 2.32.3
El "modo correcto" de trabajar con uv es no preocuparte por activar el venv. uv run y uv sync son tus dos comandos principales. El venv existe en .venv/ y está siempre sincronizado.

Comandos básicos diarios

Los seis comandos de uv que vas a usar el 95% del tiempo. Memorízalos — son tu pan de cada día.

Tabla resumen

ComandoPara qué sirve
uv add <paquete>Añadir una dependencia al proyecto
uv remove <paquete>Quitar una dependencia
uv syncSincronizar el venv con el lockfile (tras git pull)
uv run <cmd>Ejecutar un comando dentro del venv del proyecto
uv lockRegenerar el lockfile sin instalar nada
uv treeVer el árbol de dependencias del proyecto

uv add — más opciones útiles

# Añadir varias a la vez
uv add fastapi pydantic httpx

# Versión específica
uv add "django>=5.0,<6"

# Como dependencia de desarrollo (no se instala en producción)
uv add --dev pytest ruff mypy

# Desde un repositorio Git
uv add "git+https://github.com/usuario/repo.git"

# Desde un archivo local
uv add ./mi-otro-paquete

En la analogía de la construcción: uv add es darle al contratista una orden — "añade este material a la lista y consíguelo". Las dependencias --dev son la maquinaria y herramienta de obra que necesitas para construir pero que no quedan dentro del edificio (andamios, encofrados, equipo de medición).

uv sync — la operación que más vas a usar

Después de un git pull donde alguien añadió o cambió dependencias, una sola palabra deja tu venv idéntico al de tus compañeros:

uv sync

Esto:

  • Lee uv.lock y se asegura de que tu .venv/ tenga exactamente esos paquetes.
  • Instala lo que falta, elimina lo que sobra y actualiza lo que tenga la versión incorrecta.
  • Si pyproject.toml cambió pero uv.lock no se ha regenerado, lo hace automáticamente.

uv run — más allá de scripts simples

# Ejecutar un script
uv run main.py

# Ejecutar con flags de Python
uv run python -m http.server

# Ejecutar pytest, ruff, etc. (si están como --dev)
uv run pytest
uv run ruff check .

# Ejecutar con dependencias temporales (no añadidas al proyecto)
uv run --with rich main.py
Tip: uv run --with X es perfecto para probar una librería sin contaminar tu proyecto. La instala temporalmente, ejecuta y se olvida.

Ver qué tienes instalado: uv tree

uv tree
# mi-proyecto v0.1.0
# └── requests v2.32.3
#     ├── certifi v2024.7.4
#     ├── charset-normalizer v3.3.2
#     ├── idna v3.7
#     └── urllib3 v2.2.2

Útil cuando un paquete actualiza algo y rompe la compatibilidad con otro: el árbol te muestra quién depende de qué.

Actualizar dependencias

uv lock --upgrade               # actualiza TODO al máximo permitido
uv lock --upgrade-package requests  # actualiza solo requests
uv sync                          # aplica los cambios al venv
Cuidado: --upgrade respeta los rangos definidos en pyproject.toml. Si quieres ir más allá del rango, edita primero el rango en pyproject.toml.
Qué deberías poder hacer ahora
  • Instalar uv en tu sistema operativo y crear un proyecto con uv init
  • Añadir y quitar dependencias del proyecto
  • Sincronizar tu venv después de un git pull
  • Ejecutar scripts y herramientas con uv run sin activar el venv
  • Inspeccionar el árbol de dependencias y actualizarlas con seguridad

Módulo 03 Medio

Python y entornos virtuales

uv no se limita a paquetes. También descarga y gestiona versiones de Python, y crea/limpia los entornos virtuales por ti.

uv descarga Python por ti

A diferencia de pip, uv puede descargar binarios oficiales de Python (de python-build-standalone) sin pedirte que tengas Python preinstalado.

uv python install 3.12         # instala Python 3.12
uv python install 3.11 3.12 3.13   # varias a la vez
uv python list                  # ver versiones instaladas y disponibles
uv python find                  # encuentra Pythons en tu PATH

En la analogía: si los paquetes son los materiales, Python es la maquinaria base de la obra. Algunas obras requieren un equipamiento más antiguo (Python 3.10), otras uno más moderno (3.13). uv te trae el modelo correcto.

Pinear la versión: .python-version

Cuando creas un proyecto con uv init, se genera un archivo oculto:

3.12

Este archivo le dice a uv qué versión de Python usar para este proyecto. Si la versión no está instalada, uv la descarga automáticamente la primera vez que ejecutas uv sync o uv run.

uv python pin 3.13              # cambiar el pin del proyecto
Diferencia con pyenv: pyenv compila Python desde código fuente (lento y necesita librerías del sistema). uv descarga binarios precompilados — segundos en vez de minutos.

El entorno virtual .venv/

uv crea automáticamente un venv en .venv/ dentro de tu proyecto. No necesitas crearlo ni activarlo manualmente, pero si quieres puedes:

# Crear un venv manualmente (raro, uv lo hace solo)
uv venv                          # crea .venv con la versión pineada
uv venv --python 3.11            # crea con una versión específica

# Activarlo manualmente (sólo si lo necesitas)
source .venv/bin/activate        # macOS/Linux
.venv\Scripts\activate           # Windows
Filosofía recomendada: trabaja con uv run/uv sync y olvídate del venv. Pero si tu IDE necesita una ruta de Python (PyCharm, VS Code), apúntalo a .venv/bin/python.

Tabla: equivalencias con pyenv + virtualenv

Qué deberías poder hacer ahora
  • Instalar versiones de Python con uv (sin compilar)
  • Pinear una versión específica al proyecto
  • Entender por qué normalmente no necesitas activar el venv
  • Configurar tu IDE para apuntar al .venv/bin/python
Módulo 04 Medio

pyproject.toml & uv.lock

Los dos archivos que rigen tu proyecto. Entender la diferencia entre ambos es la diferencia entre "instalar paquetes" y "tener proyectos reproducibles".

pyproject.toml — las especificaciones

Es el archivo estándar de la comunidad Python (PEP 518/621) para describir un proyecto. uv añade una sección propia [tool.uv] para configuración específica.

[project]
name = "mi-app"
version = "0.1.0"
description = "API de recomendación con FastAPI"
requires-python = ">=3.12"
dependencies = [
    "fastapi>=0.110",
    "pydantic>=2.5",
    "httpx",
]

[dependency-groups]
dev = [
    "pytest>=8",
    "ruff",
    "mypy",
]
docs = [
    "mkdocs",
    "mkdocs-material",
]

[tool.uv]
# Permite versiones pre-release para algunos paquetes
prerelease = "allow"

Las claves importantes:

  • requires-python: rango aceptado de Python.
  • dependencies: lo que tu proyecto necesita siempre.
  • [dependency-groups]: grupos opcionales (dev, docs, etc.).

Manipular grupos desde la CLI

uv add --dev pytest               # al grupo "dev"
uv add --group docs mkdocs        # al grupo "docs"
uv sync --group docs              # instalar el grupo docs
uv sync --no-dev                  # sincronizar SIN dependencias dev

uv.lock — la orden de compra detallada

El lockfile registra las versiones exactas resueltas para CADA paquete y sub-paquete, junto con sus hashes criptográficos. Es lo que garantiza que tu compañero, tu CI y producción instalen exactamente lo mismo que tú.

version = 1
requires-python = ">=3.12"

[[package]]
name = "fastapi"
version = "0.110.0"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "pydantic" },
    { name = "starlette" },
]
sdist = { url = "...", hash = "sha256:abc..." }
wheels = [
    { url = "...", hash = "sha256:def..." },
]
Regla de oro: uv.lock SIEMPRE va al control de versiones (git add uv.lock). Es la única forma de garantizar reproducibilidad entre máquinas y entre commits.

El ciclo: especificaciones → lockfile → entorno

1. Editas pyproject.toml (o usas uv add)
2. uv lock         → genera/actualiza uv.lock con versiones exactas
3. uv sync         → instala uv.lock en .venv

# Para colaborar:
4. git push (con pyproject.toml + uv.lock)
5. Tu compañero: git pull + uv sync

Modos de instalación

ComandoComportamiento
uv syncSincroniza venv con lockfile, regenera lock si pyproject cambió
uv sync --frozenFalla si el lockfile no está sincronizado con pyproject (ideal en CI)
uv sync --lockedFalla si necesita tocar el lockfile
uv sync --no-install-projectSolo dependencias, no instala tu proyecto
Tip para CI: en producción y CI, usa uv sync --frozen. Si alguien hace push de un pyproject.toml sin actualizar el lockfile, el build falla y lo descubres antes de desplegar.

Inspeccionar el lockfile

uv tree                          # árbol legible
uv export --format requirements-txt > requirements.txt  # exportar para legacy
Qué deberías poder hacer ahora
  • Distinguir el rol de pyproject.toml y uv.lock
  • Definir y manejar grupos de dependencias (dev, docs, etc.)
  • Entender por qué uv.lock debe ir al repo
  • Usar uv sync --frozen en CI para detectar lockfiles desactualizados

Módulo 05 Experto

uv en producción

El módulo experto en dos partes. Primero, cómo uv reemplaza a todo el ecosistema tradicional (pip, pipx, pyenv, virtualenv, poetry). Después, los workflows que separan al que usa uv de juguete del que lo lleva a producción: scripts inline, workspaces, build & publish, CI/CD y Docker.

Parte A · Reemplazos del ecosistema

uv no es "otra herramienta más" — es UN binario que reemplaza a seis. Aquí está la tabla maestra de equivalencias y cómo migrar.

Tabla maestra de reemplazos

Herramienta tradicionalEquivalente en uvNotas
pip install Xuv pip install X o uv add XCompatible 100%
pip-compileuv pip compileMucho más rápido
virtualenvuv venvDrop-in replacement
pyenvuv python installBinarios, no compila
pipxuv tool installPara CLIs globales
poetryuv add + uv syncMismo workflow, más rápido

uv pip — modo drop-in

Si tienes scripts o documentación que asume pip, uv pip es 100% compatible:

uv pip install requests
uv pip install -r requirements.txt
uv pip uninstall requests
uv pip list
uv pip freeze
uv pip compile requirements.in -o requirements.txt
Importante: uv pip NO usa pyproject.toml ni uv.lock. Es solo un wrapper compatible con pip. Para proyectos modernos usa uv add/uv sync.

uv tool — reemplazo de pipx

Para instalar herramientas CLI globales (ruff, black, httpie, posit) en su propio entorno aislado:

uv tool install ruff             # instalar
uv tool install black mypy        # varias a la vez
uv tool list                      # listar instaladas
uv tool upgrade ruff              # actualizar
uv tool uninstall ruff            # desinstalar
uv tool run ruff check .          # ejecutar sin instalar (= uvx)

El alias uvx es equivalente a uv tool run:

uvx ruff check .                 # ruff sin instalar nada
uvx --from httpie http httpbin.org/json  # con paquete distinto al binario
Tip: uvx es perfecto para correr una herramienta de una sola vez. Cero instalación, cero contaminación.

Migrar desde requirements.txt

Si tienes un proyecto viejo con requirements.txt:

# 1. Inicializa uv en el proyecto
uv init --no-readme

# 2. Importa las dependencias del requirements
uv add -r requirements.txt

# 3. Genera el lockfile
uv lock

# 4. Verifica
uv sync

Migrar desde Poetry

uv y poetry usan el mismo formato base (pyproject.toml). Los pasos:

  1. Renombra el bloque [tool.poetry] a [project] y ajusta el formato de dependencias.
  2. Convierte { version = "^X" } a ">=X,<Y+1".
  3. Borra poetry.lock y ejecuta uv lock.
  4. Reemplaza poetry install por uv sync y poetry run por uv run.
Bonus: existen herramientas como migrate-to-uv que automatizan la conversión desde Poetry, Pipenv o Hatch.

Compatibilidad con ecosistemas existentes

  • PyPI: uv usa PyPI como índice por defecto. Mismas wheels, mismos sdists.
  • Índices privados: configurables vía --index-url, --extra-index-url o en [tool.uv].
  • requirements.txt: uv puede leerlos (uv pip install -r) y exportarlos (uv export).
  • setup.py / setup.cfg: uv los entiende para instalación, pero recomienda migrar a pyproject.toml.

Parte B · Workflows avanzados

Lo que separa a quien usa uv de juguete de quien lo lleva a producción: scripts inline, workspaces para mono-repos, build & publish, integración con CI/CD y Docker multi-stage.

B.1 · Scripts auto-contenidos (inline metadata, PEP 723)

Esta es una de las features más mágicas de uv. Puedes declarar las dependencias directamente dentro de un script de Python, en un comentario especial. uv crea un venv efímero, instala lo necesario y ejecuta — todo automático.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#     "httpx",
#     "rich",
# ]
# ///
import httpx
from rich import print

resp = httpx.get("https://api.github.com/repos/astral-sh/uv")
print(resp.json()["stargazers_count"])

Lo ejecutas con:

uv run analizar.py

uv lee el comentario, prepara el entorno (con caché para futuras ejecuciones) y lanza el script. Sin venvs visibles, sin pyproject.toml, sin instalar nada globalmente.

Casos de uso: scripts de utilidad, análisis ad-hoc, gists compartibles, automatización en bash que necesita una librería puntual. Es la respuesta de Python a npx.

Crear scripts inline rápidamente

uv init --script mi_script.py    # crea uno con la cabecera lista
uv add --script mi_script.py httpx rich   # añade deps al script

B.2 · Workspaces (mono-repos)

Un workspace permite tener varios proyectos Python en un mismo repo, con un único uv.lock compartido. Ideal para mono-repos con backend + librerías internas + cli, etc.

mi-mono-repo/
├── pyproject.toml          # workspace root
├── uv.lock                 # único, compartido
├── packages/
│   ├── core/
│   │   └── pyproject.toml  # paquete miembro
│   ├── api/
│   │   └── pyproject.toml
│   └── cli/
│       └── pyproject.toml

El pyproject.toml de la raíz declara los miembros:

[project]
name = "mi-mono-repo"
version = "0"
requires-python = ">=3.12"

[tool.uv.workspace]
members = ["packages/*"]

[tool.uv.sources]
mi-core = { workspace = true }      # api y cli usan core local

Y desde packages/api/pyproject.toml declaras mi-core como dependencia normal — uv resolverá que viene del workspace local, no de PyPI.

uv sync                    # instala TODO el workspace
uv run --package api ...   # ejecutar dentro de un miembro específico

B.3 · Build & publish a PyPI

uv puede empaquetar y publicar tu proyecto sin necesidad de twine o build:

uv build                          # genera dist/ con .whl y .tar.gz
uv build --sdist                  # solo source distribution
uv build --wheel                  # solo wheel

# Publicar a PyPI
uv publish                         # usa credenciales del .pypirc / env
uv publish --token pypi-XXX        # con token explícito
uv publish --publish-url https://test.pypi.org/legacy/   # a TestPyPI
Tip: usa trusted publishers de PyPI con GitHub Actions: cero credenciales, autenticación OIDC.

B.4 · uv en GitHub Actions

Astral mantiene una action oficial. La configuración mínima para un proyecto típico:

name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.11", "3.12", "3.13"]

    steps:
      - uses: actions/checkout@v4

      - name: Install uv
        uses: astral-sh/setup-uv@v3
        with:
          enable-cache: true

      - name: Set up Python
        run: uv python install ${{ matrix.python-version }}

      - name: Install dependencies
        run: uv sync --frozen --all-extras --dev

      - name: Lint
        run: uv run ruff check .

      - name: Test
        run: uv run pytest

Puntos clave:

  • enable-cache: true — la action cachea el directorio global de uv. La segunda corrida es casi instantánea.
  • uv sync --frozen — falla si uv.lock está desactualizado.
  • uv python install — uv descarga la versión exacta de Python; no dependes de actions/setup-python.

B.5 · Caché y configuración global

uv cachea agresivamente. Saber dónde y cómo manejarlo te ayuda en CI y al diagnosticar problemas.

Ubicación del caché

  • Linux/macOS: ~/.cache/uv/
  • Windows: %LOCALAPPDATA%\uv\cache\
uv cache dir                     # ver dónde está
uv cache clean                   # limpiar todo
uv cache prune                   # eliminar entradas obsoletas (recomendado)

Configuración persistente

Puedes definir defaults en un archivo TOML global (~/.config/uv/uv.toml en Linux/macOS) o por proyecto en la sección [tool.uv] de pyproject.toml:

[pip]
index-url = "https://mi-empresa.com/pypi/simple"
extra-index-url = ["https://pypi.org/simple"]

# Por defecto compila bytecode (.pyc) al instalar — startup más rápido
compile-bytecode = true

# Resolver más estricto
resolution = "highest"

Cuidado: uv cache clean borra todo y la siguiente instalación tardará mucho. Para mantenimiento periódico usa uv cache prune: solo elimina entradas que ya no apuntan a paquetes vivos.

B.6 · uv en Docker (multi-stage build)

El patrón recomendado: usar la imagen oficial de uv como builder y copiar el venv resultante a una imagen final mínima.

# ─── Stage 1: builder ─────────────────────────────
FROM ghcr.io/astral-sh/uv:python3.12-bookworm-slim AS builder

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PROJECT_ENVIRONMENT=/app/.venv

WORKDIR /app

# Instala deps SIN copiar el código todavía (mejor caching)
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project --no-dev

# Ahora copia el código y haz install final
COPY . .
RUN uv sync --frozen --no-dev

# ─── Stage 2: runtime ─────────────────────────────
FROM python:3.12-slim-bookworm

WORKDIR /app
COPY --from=builder /app /app

ENV PATH="/app/.venv/bin:$PATH"

CMD ["python", "-m", "mi_app"]

Por qué este patrón funciona bien:

  • El RUN uv sync de las deps se cachea: solo se reinstala si pyproject.toml/uv.lock cambian.
  • La imagen final no incluye uv ni el caché — es ligera.
  • UV_COMPILE_BYTECODE=1 mejora el startup en producción.
